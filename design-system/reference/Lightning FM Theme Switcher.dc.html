Daylight, moonlight, system

Three states cannot be a toggle. The current [ moonlight ] text button names the destination while its aria-pressed reports the current state — audit finding 17 — and a third option makes that label impossible to write honestly.

Two ways out. 2a keeps one button but shows the state you are on rather than the one you are going to, as an icon. 1a stops hiding states altogether and puts all three side by side. They share one state on this page, so switching either moves the other. Which to take depends on where it lives — see Which one.

What cycling costs, and how to pay it

Nothing tells you the third state exists

A user on daylight who wants system has to click twice, guessing, and will pass through moonlight to get there. With two states that was a non-issue; with three it is the real cost. Mitigate with a tooltip that names the next state, and accept that discovery is worse than the segmented control.

The accessible name must carry both halves

This is finding 17 again and it does not go away on its own — an icon has no text, so the label is all a screen reader gets. Use aria-label="Theme: moonlight. Change to system." — current state and next action, updated on every click. Do not use aria-pressed; the button is not a toggle. Announce the change with a live region if you want it confirmed.

System resolves to something the icon does not show

On system the half-circle says "following your OS" but not which way it landed. That is usually fine, since the page itself is the answer. It stops being fine if you ever show the icon away from the themed surface.

No spin, no crossfade

Swap the icon instantly. A rotating or morphing transition on top of an entire palette change is two animations fighting, and neither is guarded for reduced motion.

Which one

Take 2a, the icon, if it stays in the header. It is the only one that fits there honestly, and theme switching is a thing people do once — poor discovery on a once-per-install action is a fair trade.

Take 1a, the segmented control, if it moves to the footer. With the room to show all three, there is no reason to hide two of them.

Either way the storage, pre-paint and live-system notes at the bottom of this page apply unchanged — those are about behaviour, not shape.

Implementation notes

Semantics fix finding 17 for free

A role="radiogroup" with three role="radio" children and aria-checked removes the ambiguity entirely — each label names a state rather than an action, so there is no longer a mismatch between what the button says and what it reports. Add arrow-key navigation within the group.

Three storage values, not two

lfm-theme becomes "daylight" | "moonlight" | "system". Absent means system, so a first-time visitor follows their OS. Existing stored values keep working — nothing to migrate.

The pre-paint script has to resolve system

The inline script in src/app/layout.tsx currently only checks for the string "moonlight". It now needs to add the class when the stored value is moonlight or when it is missing/system and matchMedia("(prefers-color-scheme: dark)") matches. Miss this and every system-mode visitor gets a flash of the wrong theme on first paint.

System mode is live, not read-once

Subscribe to the media query's change event while system is selected, so the page follows when macOS flips at sunset with the tab open. Unsubscribe when the user picks an explicit theme. Your existing useSyncExternalStore setup in ThemeToggle.tsx already has the right shape — add the media query as a second subscription source.

Also: the desktop app

Three states matter more there than on the web — a native app that ignores the OS appearance setting feels broken on macOS. Same control, same three values, read from the system appearance API rather than matchMedia.
